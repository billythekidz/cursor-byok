# Codex adapter MVP plan

## Goal

Expose Codex as a first-class `ModelAdapter` with `type: codex`. Cursor keeps
its existing forwarder and stream lifecycle; Codex owns the shell and file
tools inside the selected workspace.

## Scope

- Detect an existing `codex` binary and report version/login state.
- Install `@openai/codex` only after an explicit dashboard action.
- Start ChatGPT OAuth through `codex login`; no token exchange is implemented
  by BYOK and no credential is returned to the frontend.
- Run `codex app-server --listen stdio://` from Go over JSONL JSON-RPC.
- Map one Cursor conversation to one persistent Codex thread.
- Stream agent text, reasoning and terminal completion into the existing
  `ModelEvent` lifecycle.
- Advertise Codex models to Cursor only when the runtime is installed and
  authenticated.

## Configuration contract

```json
{
  "type": "codex",
  "displayName": "Codex",
  "modelID": "gpt-5-codex",
  "reasoningEffort": "high",
  "active": true
}
```

`baseURL`, `apiKey`, OpenAI/Anthropic endpoint fields and custom headers are
ignored and normalized away. Auth remains in the Codex CLI `CODEX_HOME`.
Reasoning values are `low`, `medium`, `high`, `xhigh`, and `max`; `max` is sent
as `xhigh` while the runtime schema has no public `max` value. The default
sandbox is `workspace-write` and approval policy is `never`. The latter is an
MVP limitation and is shown in the model editor.

Channel IDs include the provider so a Codex model and an HTTP OpenAI adapter
cannot collide even when their model IDs match.

## Runtime setup

1. Look up `codex` on `PATH` and run `codex --version`.
2. Run `codex login status`; classify only installed/authenticated state and
   never return its raw credential material.
3. Install with `npm install --global @openai/codex`. The runner streams
   redacted output, supports cancellation and a timeout, and reports npm/Node,
   permission, and network failures.
4. Start `codex login` for browser OAuth. Headless environments can use the
   dashboard's `codex login --device-auth` fallback through the same process
   lifecycle.

## Protocol subset

The client uses newline-delimited JSON, incrementing request IDs, a pending
request map, notification dispatch, stderr separation, process-exit
detection, context cancellation and lifecycle ownership by the runtime manager.
The implemented calls are:

- `initialize` / `initialized`
- `thread/start`
- `thread/resume`
- `turn/start`
- `turn/interrupt`

The adapter consumes `item/agentMessage/delta`, reasoning deltas,
`item/commandExecution/outputDelta`, file progress, `turn/completed`, and
`error`. Dynamic tools, interactive approvals and `item/tool/call` are outside
the MVP.

## Request and persistence rules

The first non-empty workspace path becomes Codex `cwd`. Only the latest Cursor
user input is sent to `turn/start`; the complete Cursor transcript is not
replayed into Codex because the Codex thread already owns its history. Cursor's
existing semantic history remains append-only and receives only the model
delta/metadata generated by the normal forwarder lifecycle.

The mutable mapping is stored beside the conversation history as
`history/<conversationId>/codex.json`:

```json
{
  "provider": "codex",
  "modelID": "gpt-5-codex",
  "codexThreadID": "thread_...",
  "workspace": "D:\\workspace",
  "runtimeVersion": "..."
}
```

Mapping reuse requires matching workspace, model and (when available) runtime
version. A failed resume starts a new thread and leaves the old thread
isolated from the new provider pass. The runtime manager serializes turns per
thread and interrupts using the active request context.

## Verification

- `go build .` and targeted `go build ./internal/...` packages.
- `npm run build` in `frontend/` so source literals and locale catalogs are
  regenerated by the scanner.
- Manual smoke checks: missing binary, install failure, OAuth login, normal
  text streaming, workspace edit, follow-up resume, service restart and
  app-server exit/restart.
- Inspect redacted stderr/protocol artifacts; no API key, OAuth token or
  credential payload may appear in UI or logs.

No repository test files are added for this MVP because this repository's
current test-authoring policy forbids adding tests.

## Deferred work

Dynamic tool bridging, interactive approvals, bundled binaries, background
upgrades, multiple accounts, remote app-server transports, MCP mirroring and
cross-conversation thread sharing remain post-MVP.
